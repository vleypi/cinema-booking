# ИС «Луч»

**Информационная система продажи билетов сети кинотеатров: сайт для зрителей, приложение персонала с кассой и сканером QR-кодов и общее серверное API.**

> **Проект находится в активной разработке.** Завершены этапы 1 и 2: техническое задание, проект базы данных, серверное API и приложение персонала для управления кинотеатром. Клиентское приложение для покупки билетов разрабатывается на этапе 3.

ИС «Луч» автоматизирует продажу билетов и контроль прохода зрителей в кинотеатрах сети «Луч». Клиенты покупают билеты на сайте и получают их на почту. Сотрудники ведут афишу и расписание, продают билеты в кассе и пропускают зрителей по QR-коду с камеры телефона.

*Семестровый командный проект по дисциплине «Создание программного обеспечения», РТУ МИРЭА.*

## Проблема

Кинотеатр продаёт билеты через несколько каналов: на сайте и в кассе. Если каналы не связаны, одно место можно продать двум покупателям, а продажи приходится сводить в отчёты вручную. Изменение афиши и цен требует участия разработчиков, а проверка бумажного билета на входе отнимает время.

Система хранит все продажи кинотеатра в одной базе независимо от канала. Место удерживается за покупателем на время оплаты, поэтому двойная продажа исключена. Администрация сама меняет расписание и цены через приложение персонала. Контролер проверяет билет за несколько секунд по QR-коду.

Сеть с первого дня поддерживает несколько кинотеатров. Залы, сеансы и заказы привязаны к кинотеатру, каталог фильмов общий для всей сети.

## Функционал

### Реализовано (этапы 1 и 2)

- Вход сотрудника по логину и паролю. Временный пароль нужно сменить при первом входе.
- Пять ролей персонала по матрице прав из ТЗ: суперадминистратор, администратор, менеджер, кассир и контролер. Меню приложения строится по роли.
- Привязка сотрудника к кинотеатрам. Сотрудник видит данные только своих кинотеатров, суперадминистратор видит всю сеть.
- Управление кинотеатрами сети и сотрудниками.
- Залы с визуальным редактором схемы: ряды, места, проходы и ценовые зоны. Изменение схемы создаёт новую версию, поэтому проданные билеты сохраняют свои места.
- Ценовые зоны зала и временные интервалы суток со своими коэффициентами.
- Общий каталог фильмов с загрузкой постеров.
- Расписание сеансов с проверкой часов работы кинотеатра и перерыва между сеансами в зале.
- Поиск, сортировка и постраничный вывод во всех списках приложения персонала.
- Единый формат ошибок API с сообщениями по каждому полю формы.
- Документация API в Swagger.
- E2E-тесты API, включая проверку прав каждой роли и доступа к чужому кинотеатру.

### Дальше по плану

- **Этап 3**: клиентское приложение с афишей, схемой зала и бронью мест. Оплата через ЮKassa в тестовом режиме, вход клиента по коду из письма, личный кабинет. PDF с билетами и письма.
- **Этап 4**: касса и сканер QR-кода в приложении персонала. Возвраты в кассе и в личном кабинете, отмена сеанса, отчёты и журнал действий.
- **Этап 5**: требования с приоритетом Should, регрессионное тестирование и подготовка демонстрации.

## Технологический стек

- **TypeScript**: общий язык серверной и клиентской частей.
- **pnpm workspaces, Turborepo**: монорепозиторий с общим кэшем сборки и едиными версиями зависимостей.
- **Next.js 16, React 19, Tailwind CSS 4**: клиентское приложение и приложение персонала.
- **TanStack Query, Axios**: запросы к API и кэширование серверных данных.
- **React Hook Form, zod**: формы и их валидация.
- **NestJS**: серверное API, валидация входных данных через class-validator, документация в Swagger.
- **PostgreSQL, TypeORM**: хранение данных, схема меняется только миграциями.
- **Redis, BullMQ** *(этап 3)*: брони мест, одноразовые коды и очереди фоновых задач.
- **JWT в HttpOnly cookie**: сессии персонала и клиентов без хранения токенов в JavaScript.
- **Vitest**: модульные и e2e-тесты серверного API.
- **Docker Compose, GitHub Actions**: запуск системы в контейнерах и проверка каждого запроса на слияние.

## Архитектура

Оба фронтенда обращаются к API по адресу `/api` на своём домене. Next.js перенаправляет такие запросы на серверное API, поэтому cookie входа принадлежат домену приложения. Proxy приложения проверяет сессию до рендера страницы и обновляет пару токенов, если access-токен истёк.

```text
frontend/cinema (зрители)   frontend/crm (персонал)
            |                          |
            +--- /api ---+---- /api ---+
                         |
                  backend (NestJS)
                         |
          +--------------+--------------+
          |              |              |
     PostgreSQL        Redis      storage/media
   (данные системы) (брони, коды,   (постеры)
                      очереди)
```

Серверное API разделено на модули по предметным областям: `auth`, `staff`, `cinemas`, `halls`, `time-bands`, `films`, `sessions`, `media`. Контроллер модуля принимает DTO и вызывает сервис, бизнес-правила живут в сервисах. Права проверяет один `AuthGuard` по декоратору `@Auth(Permission.X)`.

Фронтенды построены по методологии Feature-Sliced Design со слоями `app`, `views`, `widgets`, `features`, `entities` и `shared`. Код, нужный обоим приложениям, лежит в пакете `@luch/shared`.

## Модель данных

Данные кинотеатра хранятся с привязкой к нему: залы, версии схем, ценовые зоны, временные интервалы и сеансы. Фильмы образуют общий каталог сети. Сотрудник связан с кинотеатрами отдельной таблицей привязок. Деньги хранятся целым числом в копейках, даты хранятся в UTC и показываются в часовом поясе кинотеатра.

Полная ER-диаграмма лежит в [docs/project/ER.pdf](docs/project/ER.pdf).

## Установка и запуск

### В Docker

Для запуска нужны Docker и Docker Compose. Перед первым запуском задайте секрет JWT длиной не меньше 32 символов и пароль суперадминистратора:

```bash
export JWT_ACCESS_SECRET="$(openssl rand -hex 32)"
export SEED_SUPER_ADMIN_PASSWORD="Admin-Password-1"
docker compose -f docker/docker-compose.yml up --build
```

Миграции и начальные данные применяются при старте сервера. После запуска доступны адреса:

- приложение персонала: [http://localhost:3002](http://localhost:3002);
- клиентское приложение: [http://localhost:3001](http://localhost:3001);
- серверное API: [http://localhost:3000/api](http://localhost:3000/api);
- документация API: [http://localhost:3000/api/docs](http://localhost:3000/api/docs).

Остановить контейнеры:

```bash
docker compose -f docker/docker-compose.yml down
```

### Для разработки

Потребуются Node.js 24 или новее, pnpm и Docker для базы данных.

```bash
pnpm install
cp backend/.env.example backend/.env
docker compose -f docker/docker-compose.yml up -d postgres redis
pnpm --filter backend start:dev
pnpm dev
```

Команда `pnpm dev` запускает оба фронтенда с горячей перезагрузкой. Сервер стартует отдельной командой и читает настройки из `backend/.env`.

### Проверки

```bash
pnpm check
pnpm db:test
pnpm test:e2e
```

`pnpm check` прогоняет линтер, модульные тесты, сборку и проверку типов, то же самое делает CI. `pnpm db:test` поднимает тестовые PostgreSQL на порту 5433 и Redis на порту 6380, после чего `pnpm test:e2e` запускает e2e-тесты API.

## Пример использования

1. Откройте приложение персонала и войдите как суперадминистратор с логином `admin` и паролем из `SEED_SUPER_ADMIN_PASSWORD`.
2. Создайте кинотеатр и укажите его часовой пояс и часы работы.
3. Заведите администратора кинотеатра. При первом входе он сменит временный пароль.
4. Добавьте зал и нарисуйте его схему в редакторе: ряды, места, проходы и ценовые зоны.
5. Задайте временные интервалы суток с коэффициентами цены.
6. Добавьте фильм в каталог и загрузите постер.
7. Поставьте сеансы фильма в расписание зала.
