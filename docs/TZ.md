# 2 Назначение и цели создания системы

## 2.1 Назначение системы

Система автоматизирует продажу билетов и контроль прохода зрителей в кинотеатрах сети «Луч». Клиенты покупают билеты на сайте. Сотрудники ведут расписание, продают билеты в кассе и пропускают зрителей по QR-коду.

## 2.2 Цели создания системы

Цель 1. Клиент покупает билет на сайте не более чем за пять минут от выбора сеанса до получения письма с билетом.

Цель 2. Система исключает продажу одного места двум покупателям.

Цель 3. Все продажи кинотеатра хранятся в одной базе независимо от канала. Онлайн-продажи и продажи в кассе попадают в общие отчеты.

Цель 4. Контролер проверяет билет на входе за несколько секунд с помощью камеры телефона.

Цель 5. Администрация кинотеатра меняет афишу, расписание и цены без участия разработчиков.

Цель 6. Архитектура системы позволяет подключить новые кинотеатры сети без переработки кода.

## 2.3 Границы проекта

В рамках проекта команда не реализует следующие функции:

- продажу еды и напитков бара;
- промокоды, скидки и программу лояльности;
- подарочные сертификаты;
- отзывы и рейтинги фильмов;
- нативные мобильные приложения для iOS и Android;
- интерфейс на иностранных языках;
- прием реальных платежей. Оплата работает в тестовом режиме ЮKassa.

# 4 Требования к системе

## 4.1 Требования к структуре системы

### 4.1.1 Состав системы

Система состоит из следующих частей.

Таблица 4. Состав системы

| Часть | Назначение |
|---|---|
| Клиентское приложение | Сайт для покупателей. Показывает афишу и расписание. Позволяет выбрать места, оплатить заказ и вернуть билеты |
| Приложение персонала | Закрытый сайт для сотрудников. Работает на компьютере и на телефоне как PWA. Содержит управление сетью, кассу и сканер билетов |
| Серверное API | Хранит бизнес-логику системы. Принимает запросы обоих приложений и уведомления ЮKassa |
| Фоновые задачи | Формируют PDF с билетами и отправляют письма. Освобождают просроченные брони |
| Реляционная база данных | Хранит постоянные данные системы |
| Хранилище в памяти | Хранит брони мест, одноразовые коды и очереди фоновых задач |
| Файловое хранилище | Хранит постеры фильмов |

### 4.1.2 Поддержка сети кинотеатров

Все данные о залах, сеансах, заказах и отчетах система хранит с привязкой к кинотеатру. Каталог фильмов общий для всей сети. Фильм заводится один раз, а сеансы на него ставятся в каждом кинотеатре отдельно.

Клиент выбирает кинотеатр на сайте. Система запоминает выбор и показывает расписание только этого кинотеатра. Адрес страницы содержит код кинотеатра. Пока в сети один кинотеатр, выбор скрыт.

Сотрудник видит данные только тех кинотеатров, к которым его привязал администратор. Суперадминистратор видит всю сеть.

### 4.1.3 Структура репозитория

Код системы хранится в одном репозитории. Пакетами репозитория управляют pnpm workspaces и Turborepo. Репозиторий содержит следующие каталоги:

- backend для серверного API;
- frontend/cinema для клиентского приложения;
- frontend/crm для приложения персонала;
- frontend/shared для общего кода обоих приложений;
- docker для файлов Docker Compose;
- docs для документации.

Каталог frontend/shared избавляет приложения от копирования кода. В нем лежат:

- клиент для запросов к API;
- типы данных API;
- схемы валидации форм;
- общие компоненты интерфейса;
- общие настройки линтера и TypeScript.

### 4.1.4 Архитектура кода

Клиентское приложение и приложение персонала построены по методологии FSD. Код каждого приложения делится на слои app, views, widgets, features, entities и shared. Слой обращается только к слоям ниже себя. Модуль слоя открывает другим модулям только свой публичный интерфейс.

Серверное API делится на модули NestJS по предметным областям. Контроллер модуля принимает запрос и передает его сервису. Бизнес-правила выполняются в сервисах.

Код системы следует принципам SOLID и DRY. Каждый файл отвечает за одну задачу. Повторяющаяся логика выносится в общий модуль.

Оба приложения обращаются к серверному API по адресу /api на своем домене. Next.js перенаправляет такие запросы на серверное API, поэтому cookie входа принадлежат домену приложения.

## 4.3 Бизнес-правила

Бизнес-правила обязательны для всех каналов продаж. Серверное API проверяет каждое правило самостоятельно и не доверяет проверкам на стороне интерфейса.

**Цены**

BR-01. Цена места рассчитывается по формуле: базовая цена × коэффициент временного интервала × коэффициент ценовой зоны. Результат округляется до 10 рублей.

BR-02. Базовая цена берется из сеанса. Если менеджер не задал цену сеанса, система берет базовую цену зала.

BR-03. Администратор настраивает временные интервалы и их коэффициенты для каждого кинотеатра. Начальные значения: до 12:00 коэффициент 0,825; с 12:00 до 17:00 коэффициент 1,0; после 17:00 коэффициент 1,2.

BR-04. Для отдельного зала администратор может отключить временные коэффициенты. Так работает зал «Диван» с фиксированной ценой.

BR-05. Цена билета фиксируется в момент создания заказа. Последующее изменение цен не влияет на оплаченные и забронированные билеты.

**Расписание**

BR-06. Сеансы в одном зале не пересекаются. Между окончанием одного сеанса и началом следующего проходит технический перерыв. Длительность перерыва задает администратор кинотеатра, начальное значение составляет 15 минут.

BR-07. Окончание сеанса система вычисляет как время начала плюс длительность фильма.

BR-08. Сеанс нельзя создать в прошлом или вне часов работы кинотеатра.

BR-09. Сеанс с проданными билетами нельзя удалить. Его можно только отменить.

BR-10. При отмене сеанса система возвращает деньги за все активные билеты и отправляет клиентам письмо об отмене.

**Схемы залов**

BR-11. Схему зала нельзя изменить после появления на ней хотя бы одного сеанса. Администратор создает новую версию схемы, и новые сеансы используют ее. Старые сеансы сохраняют свою версию.

BR-12. Место схемы имеет один из типов: кресло, диван на двоих, место для кресла-коляски.

**Бронь и покупка**

BR-13. Онлайн-заказ содержит не более пяти билетов. Заказ в кассе не ограничен по количеству билетов.

BR-14. Все билеты заказа относятся к одному сеансу.

BR-15. Онлайн-продажа на сеанс закрывается за 10 минут до его начала. Касса продает билеты до окончания сеанса.

BR-16. При переходе к оплате система бронирует выбранные места на 10 минут. Если оплата не поступила за это время, заказ переходит в статус «Просрочен», а места освобождаются.

BR-17. Одно место на сеансе может принадлежать только одному активному билету или одной активной брони. Ограничение действует на уровне базы данных и защищает от одновременной покупки.

BR-18. На фильм с возрастным ограничением 18+ клиент подтверждает свой возраст отметкой в форме заказа. Контролер проверяет возраст на входе.

**Клиенты**

BR-19. Клиента определяет адрес электронной почты. При первой покупке на новый адрес система создает запись клиента без пароля. Все заказы на этот адрес привязываются к этой записи.

BR-20. Клиент входит в личный кабинет по одноразовому коду из письма. Первый успешный вход подтверждает адрес почты.

BR-21. Заказы видит только клиент с подтвержденной почтой. Поэтому человек, который указал чужой адрес при покупке, не получает доступа к заказам владельца адреса.

BR-22. Одноразовый код состоит из шести цифр и действует 10 минут. На ввод кода дается пять попыток. Новый код можно запросить не чаще одного раза в минуту.

BR-23. Продажа в кассе создает заказ без привязки к клиенту. Если покупатель назвал адрес почты, заказ привязывается к клиенту по правилу BR-19.

**Билеты и проход**

BR-24. Каждый билет получает уникальный код из десяти символов. Код содержит только заглавные латинские буквы и цифры без похожих знаков.

BR-25. QR-код билета содержит код билета и криптографическую подпись сервера. Подделать билет подбором номера нельзя.

BR-26. Контролер пропускает зрителя с 30 минут до начала сеанса и до его окончания.

BR-27. По одному билету можно пройти только один раз. После прохода билет получает статус «Использован».

BR-28. Система отказывает в проходе в следующих случаях:

- билет уже использован;
- билет возвращен;
- сеанс отменен;
- билет относится к другому залу или другому кинотеатру;
- время прохода еще не наступило или уже прошло.

При отказе сканер показывает причину. Для использованного билета сканер показывает время прохода и сотрудника, который пропустил зрителя.

**Возвраты**

BR-29. Клиент вправе вернуть билет до начала сеанса. Правило следует из статьи 32 Закона «О защите прав потребителей».

BR-30. Система возвращает полную стоимость билета без удержаний.

BR-31. Возврат оформляется на каждый билет отдельно. Клиент может вернуть часть билетов заказа.

BR-32. Деньги за онлайн-покупку система возвращает через ЮKassa на карту покупателя. Деньги за покупку в кассе кассир возвращает наличными или на карту через терминал.

BR-33. Использованный билет вернуть нельзя.

## 4.5 Основные сценарии использования

Раздел описывает базовые сценарии. Альтернативные ветки указаны только для частых ошибок.

**UC-01. Покупка билета онлайн**

Участник: гость.

Основной сценарий:

1. Гость открывает сайт и выбирает кинотеатр.
2. Гость выбирает дату и сеанс в расписании.
3. Система показывает схему зала со свободными местами и ценами.
4. Гость выбирает два места и нажимает «Продолжить».
5. Гость вводит адрес почты и подтверждает заказ.
6. Система бронирует места на 10 минут и создает заказ в статусе «Ожидает оплаты».
7. Система перенаправляет гостя на страницу оплаты ЮKassa.
8. Гость оплачивает заказ картой.
9. ЮKassa уведомляет серверное API об успешной оплате.
10. Система проверяет платеж через API ЮKassa и переводит заказ в статус «Оплачен».
11. Система создает клиента по адресу почты, если такого клиента еще нет.
12. Фоновая задача формирует PDF с билетами и отправляет письмо.
13. Гость видит страницу заказа с билетами.

Альтернативные ветки:

4а. Другой покупатель занял место раньше. Система сообщает об этом и обновляет схему.

8а. Гость не оплатил заказ за 10 минут. Заказ получает статус «Просрочен», места освобождаются.

8б. Оплата отклонена банком. Гость может повторить оплату, пока действует бронь.

**UC-02. Вход клиента и просмотр билетов**

Участник: клиент.

1. Клиент нажимает «Войти» и вводит адрес почты.
2. Система отправляет шестизначный код на почту.
3. Клиент вводит код.
4. Система подтверждает почту и открывает личный кабинет.
5. Клиент видит все свои заказы, включая покупки в кассе с этой почтой.
6. Клиент открывает заказ и показывает QR-код билета с экрана телефона.

Альтернативная ветка:

3а. Клиент пять раз ввел неверный код. Система аннулирует код и предлагает запросить новый.

**UC-03. Возврат билета клиентом**

Участник: клиент.

1. Клиент открывает заказ в личном кабинете или переходит по ссылке из письма.
2. Клиент отмечает один билет из трех и нажимает «Вернуть».
3. Система показывает сумму возврата.
4. Клиент подтверждает возврат.
5. Система создает возврат в ЮKassa и переводит билет в статус «Возвращен».
6. Место снова становится доступным для продажи.
7. Клиент получает письмо о возврате.

Альтернативная ветка:

1а. Сеанс уже начался. Система сообщает, что вернуть билет нельзя.

**UC-04. Настройка нового зала**

Участник: администратор.

1. Администратор открывает раздел «Залы» и нажимает «Добавить зал».
2. Администратор вводит название, формат и базовую цену.
3. В редакторе администратор задает 7 рядов по 10 мест и проход после пятого места.
4. Администратор выделяет два крайних места последнего ряда и назначает им тип «Место для кресла-коляски».
5. Администратор назначает ценовые зоны и сохраняет схему.
6. Система сохраняет первую версию схемы и записывает действие в журнал.

**UC-05. Добавление сотрудника**

Участник: администратор.

1. Администратор открывает раздел «Сотрудники».
2. Администратор вводит имя, логин и роль «Кассир».
3. Система создает сотрудника с привязкой к кинотеатру администратора и временным паролем.
4. При первом входе сотрудник меняет временный пароль.

**UC-06. Добавление фильма и сеансов**

Участник: менеджер.

1. Менеджер открывает раздел «Фильмы» и добавляет новый фильм с постером.
2. Менеджер открывает раздел «Расписание» и выбирает зал и дату.
3. Менеджер ставит фильм на 19:45 и задает повышенную базовую цену для премьеры.
4. Система проверяет пересечения с другими сеансами и технический перерыв.
5. Система сохраняет сеанс, и сеанс появляется на сайте.

Альтернативная ветка:

4а. Сеанс пересекается с другим сеансом. Система показывает конфликтующий сеанс и не сохраняет новый.

**UC-07. Отмена сеанса**

Участник: менеджер.

1. Менеджер открывает сеанс и нажимает «Отменить сеанс».
2. Система показывает количество проданных билетов и сумму возврата.
3. Менеджер подтверждает отмену и указывает причину.
4. Система отменяет сеанс и снимает его с сайта.
5. Система возвращает деньги за все онлайн-билеты через ЮKassa.
6. Система отправляет письмо каждому покупателю с указанной почтой.
7. Билеты из кассы получают отметку «Ожидает возврата в кассе».

**UC-08. Продажа в кассе**

Участник: кассир.

1. Кассир выбирает сеанс и места на схеме зала.
2. Покупатель называет адрес почты, и кассир вводит его.
3. Кассир принимает оплату наличными и отмечает способ оплаты.
4. Система создает оплаченный заказ с каналом «Касса».
5. Кассир печатает билеты и отдает их покупателю.
6. Система отправляет PDF с билетами на почту покупателя.

**UC-09. Проход зрителя в зал**

Участник: контролер.

1. Контролер открывает сканер на телефоне и выбирает зал.
2. Зритель показывает QR-код на экране телефона или на распечатке.
3. Сканер считывает код и отправляет его на сервер.
4. Система проверяет подпись и правила прохода.
5. Сканер показывает зеленый экран с фильмом, рядом и местом.
6. Система переводит билет в статус «Использован».

Альтернативные ветки:

3а. Код не считывается. Контролер вводит код билета вручную.

4а. Билет уже использован. Сканер показывает красный экран, время прохода и сотрудника, который пропустил зрителя.

### 4.6.2 Временные данные

Следующие данные живут ограниченное время, поэтому система хранит их в Redis:

- брони мест с временем жизни 10 минут;
- хеши одноразовых кодов входа с временем жизни 10 минут и счетчиком попыток;
- счетчики ограничения частоты запросов;
- очереди фоновых задач.

Бронь в Redis ускоряет показ схемы зала. Окончательную защиту от двойной продажи обеспечивает уникальный индекс в базе данных.

### 4.6.3 Связи сущностей

- Кинотеатр содержит залы, временные интервалы и заказы.
- Зал содержит версии схемы и ценовые зоны.
- Версия схемы содержит места.
- Сеанс ссылается на фильм, зал и версию схемы.
- Заказ ссылается на сеанс и содержит билеты и платежи.
- Клиент владеет заказами.
- Возврат ссылается на платеж и через RefundTicket связан с билетами.
- Сотрудник привязан к кинотеатрам через StaffCinema.

ER-диаграмма входит в комплект документации этапа 1.

## 4.7 Нефункциональные требования

### 4.7.1 Производительность

NFR-01. Сервер отвечает на 95 % запросов чтения быстрее 300 мс при 50 одновременных пользователях.

NFR-02. Проверка билета сканером занимает не более одной секунды от считывания кода до показа результата.

NFR-03. Письмо с билетами уходит не позднее одной минуты после оплаты.

### 4.7.2 Надежность

NFR-04. Повторное уведомление ЮKassa об одной оплате не создает повторных билетов. Обработка уведомлений идемпотентна.

NFR-05. Ошибка отправки письма не отменяет заказ. Фоновая задача повторяет отправку до пяти раз с растущей паузой.

NFR-06. Все изменения схемы базы данных выполняются через миграции TypeORM. Автоматическая синхронизация схемы запрещена во всех окружениях, кроме тестового.

### 4.7.3 Безопасность

NFR-07. Серверное API проверяет роль и привязку к кинотеатру в каждом запросе персонала.

NFR-08. Клиент получает доступ только к своим заказам. Запрос чужого заказа возвращает ошибку 404.

NFR-09. Токен доступа живет 15 минут. Токен доступа и токен продления хранятся только в cookie с флагами HttpOnly, Secure и SameSite. Токен продления меняется при каждом использовании. Серверное API не принимает токены в заголовке Authorization, а клиентский код не читает и не хранит токены.

NFR-10. Пароли сотрудников хранятся в виде хеша bcrypt или argon2.

NFR-11. Система ограничивает частоту запросов к входу, отправке кода и проверке билета.

NFR-12. Серверное API принимает уведомление ЮKassa только после проверки платежа запросом к API ЮKassa.

NFR-13. Логи не содержат паролей, кодов входа, токенов и полных данных карт.

NFR-14. Все входные данные API проходят валидацию по DTO. Запросы к базе данных строятся только через параметризованные запросы TypeORM.

NFR-15. Секреты хранятся в переменных окружения и не попадают в репозиторий.

### 4.7.4 Персональные данные

NFR-16. Система хранит только необходимые персональные данные: почту, имя и телефон клиента.

NFR-17. Форма заказа содержит ссылку на политику обработки персональных данных и отметку согласия.

### 4.7.5 Удобство использования

NFR-18. Клиентское приложение корректно работает на экранах шириной от 360 пикселей.

NFR-19. Сканер рассчитан на работу одной рукой на телефоне.

NFR-20. Интерфейсы соответствуют уровню AA рекомендаций WCAG 2.1 по контрасту и работе с клавиатуры.

NFR-21. Интерфейс и письма написаны на русском языке. Время показывается в часовом поясе кинотеатра.

### 4.7.6 Совместимость

NFR-22. Приложения работают в двух последних версиях браузеров Chrome, Firefox, Safari и Яндекс Браузер.

NFR-23. Сканер работает в Chrome для Android и Safari для iOS.

Структура базы данных описана в разделе 4.6. Начальные данные загружаются скриптом заполнения. Скрипт создает первый кинотеатр с тремя залами, суперадминистратора, демонстрационные фильмы и расписание на семь дней.

### 4.8.3 Техническое обеспечение

Для разработки и демонстрации достаточно компьютера разработчика с Docker. Все части системы запускаются одной командой Docker Compose. Для проверки сканера нужен телефон с камерой в одной сети с компьютером.

Развертывание на внешнем сервере с доменным именем имеет приоритет Should.

## 4.9 Требования к интеграции

### 4.9.1 ЮKassa

Система создает платеж через API ЮKassa с ключом идемпотентности. Клиент оплачивает заказ на странице ЮKassa и возвращается на сайт.

ЮKassa присылает уведомления о событиях payment.succeeded, payment.canceled и refund.succeeded.

Возврат создается через API ЮKassa на сумму выбранных билетов.

Интеграция работает с тестовым магазином и тестовыми картами ЮKassa.

### 4.9.2 Почта

Система отправляет письма через SMTP. В разработке письма попадают в MailHog, и их можно посмотреть в браузере. Письма формируются по HTML-шаблонам с текстовой версией.

### 4.9.3 Файловое хранилище

Постеры загружаются в MinIO. Клиентское приложение получает постеры по публичной ссылке. Next.js оптимизирует изображения при показе.

# 6 Порядок разработки системы

## 6.1 Управление задачами

Руководитель команды ведет задачи в общей таблице. Задача содержит исполнителя, описание, критерий готовности, зависимости, ссылку на требование ТЗ и статус. Каждая задача ссылается на идентификатор требования, например FR-C06 или BR-17.

## 6.2 Работа с репозиторием

- Каждая задача выполняется в отдельной ветке. Префикс ветки совпадает с типом изменения из docs/COMMIT_CONVENTION.md, например feat/, fix/, docs/ или test/.
- Сообщения коммитов оформляются по соглашению Conventional Commits на русском языке. Правила приведены в файле docs/COMMIT_CONVENTION.md.
- Изменения попадают в ветку main только через запрос на слияние. Запрос на слияние проверяет и принимает руководитель команды.
- GitHub Actions запускает линтер, проверку типов, тесты и сборку для каждого запроса на слияние. Запрос с ошибками не принимается.

## 6.3 Критерии готовности задачи

Задача считается выполненной при соблюдении всех условий:

- код соответствует критериям приемки требования;
- код соблюдает архитектуру из раздела 4.1.4;
- линтер, проверка типов и тесты проходят в CI;
- новая серверная логика покрыта тестами;
- новые эндпоинты описаны в Swagger;
- руководитель команды одобрил запрос на слияние;
- задача переведена в статус «Готово» в таблице задач.

## 7.1 Виды испытаний

|---|---|---|

## 7.2 Проверка безопасности

Инженер по тестированию проверяет систему на следующие уязвимости:

- доступ к чужому заказу подменой идентификатора;
- доступ сотрудника к данным чужого кинотеатра;
- выполнение действий сверх прав роли;
- подбор одноразового кода;
- подделку QR-кода и подбор кода билета;
- повторное использование ссылки на возврат;
- одновременную покупку одного места двумя клиентами;
- поддельное уведомление об оплате;
- SQL-инъекции и XSS;
- утечку чувствительных данных в логах и ответах API.

## 7.3 Учет дефектов

Дефекты регистрируются в GitHub Issues по шаблону. Шаблон содержит шаги воспроизведения, ожидаемый результат, фактический результат, окружение и серьезность. Запрос на слияние в модулях booking, payments и auth не принимается без тестов. По итогам каждого этапа инженер по тестированию готовит отчет о тестировании.

## 7.4 Приемка системы

Система считается принятой после выполнения следующих условий:

- все требования с приоритетом Must реализованы и проходят критерии приемки;
- сценарии UC-01 и UC-09 проходят на демонстрации без ошибок;
- в системе нет открытых дефектов критической и высокой серьезности;
- система запускается по инструкции на чистом компьютере одной командой;
- комплект документации из раздела 8 передан преподавателю.
